SVN vs Git: Why Going Back to SVN Felt Like Time Travel

A software engineer's take on version control after a return trip to TortoiseSVN

2026-11-24

Recently I got the chance to work with Subversion (SVN) through TortoiseSVN again, for the first time since my previous job. I use Git almost every day, so the switch back was... an experience. I can't really express how archaic it felt.

So I started thinking: is SVN actually bad, or have I just been spoiled by Git? That led me to write this post, a fair look at both, from someone who ships code for a living.

TL;DR - The Key Takeaways

  • SVN is centralized, Git is distributed — and that one difference changes almost everything about the daily workflow.
  • Git commits are local, fast, and cheap — SVN commits go straight to the server, so you hesitate before every one.
  • Branching and merging is where Git wins big — in SVN, branches are folder copies and merges feel like a chore.
  • SVN is not useless — it still has real strengths with large binary files, partial checkouts, and path-based permissions.
  • My verdict: for most software teams, Git is the better default. SVN isn't wrong, it just feels like it belongs to another era.

What SVN Really Is

SVN follows a client-server model. There is one central repository, and every developer checks out a working copy from it. Your changes only "exist" in the history once they are committed to that central server.

The Mental Model

  • One source of truth: the server holds the full history, your machine holds a snapshot.
  • Global revision numbers: every commit bumps a single number for the whole repo (r1042, r1043, ...).
  • Atomic commits: a commit either fully succeeds or not at all, which was a big step up from CVS.

It's simple, and honestly, for its time it was great. The problem is how much the world has moved on since.

The Core Difference: Centralized vs Distributed

With Git, every clone is a full repository — complete history, all branches, everything. You can commit, branch, diff, and browse history on a plane with no Wi-Fi. With SVN, most of those operations need a round trip to the server.

That sounds like a small technical detail, but it shapes your behavior. In Git you commit early and often because commits are private and free. In SVN, every commit is public and immediate, so you end up batching a day's work into one big commit and hoping it doesn't break the build for everyone.

Day-to-Day Workflow

Here is roughly what a basic feature workflow looks like in each:

SVN

svn update
# ...make changes...
svn commit -m "Add login validation"

Git

git switch -c feature/login-validation
# ...make changes...
git add .
git commit -m "Add login validation"
git push origin feature/login-validation

On paper, SVN looks shorter. In practice, Git's extra steps give you something SVN never does: a safe place to work. Your branch is yours, your commits can be amended, split, or squashed before anyone else sees them, and a mistake is almost always recoverable.

In SVN, if someone commits before you, you get the dreaded "out of date" error and have to update (and possibly resolve conflicts) before you can even commit your own work.

Branching and Merging

This is the part that hurt the most.

In SVN

  • A branch is a copy of a directory in the repo (/branches/my-feature). Cheap on the server, but heavy on the mindset.
  • Switching means svn switch, and merging back means tracking what has already been merged.
  • Tree conflicts (renamed or moved files) can turn a simple merge into an afternoon of pain.

In Git

  • A branch is a lightweight pointer. Creating one takes milliseconds.
  • Merging and rebasing are first-class operations with well-understood behavior.
  • Feature branches, pull requests, and code review are the default way of working.

In Git, I branch without thinking about it. In SVN, I caught myself avoiding branches because the cost felt too high. When a tool makes you avoid good practices, that's a design problem.

The Staging Area, Stash, and Other Things I Missed

Going back to SVN, I kept reaching for tools that simply weren't there:

  • Staging area: in Git I can commit only the changes I want. In SVN, it's basically "commit everything you ticked", with no partial-hunk staging.
  • Stash: need to switch context quickly? git stash and move on. In SVN you're juggling patch files.
  • Interactive rebase: cleaning up messy history before sharing it is a Git superpower.
  • Bisect: git bisect hunts down the commit that introduced a bug automatically.
  • Local history: git log, git blame and git diff are instant. In SVN they depend on the server.

The TortoiseSVN Experience

To be fair to TortoiseSVN: it's a genuinely well-made tool. The Windows Explorer integration, the overlay icons showing modified or conflicted files, and the right-click menus are polished and approachable. If you're someone who doesn't live in a terminal, it makes SVN far less intimidating.

But a nice UI can't hide the workflow underneath. You still wait on the network for operations that should be instant, you still can't commit offline, and you still end up with a working copy full of hidden metadata. It felt like driving a beautifully restored classic car: lovely to look at, but I'd really rather have the modern one for my daily commute.

The Ecosystem Gap

Git didn't win only because of its design. It won because of everything built around it:

  • Hosting platforms like GitHub, GitLab, and Bitbucket
  • Pull requests and code review as a standard workflow
  • CI/CD integration that assumes Git out of the box
  • Community knowledge — almost any Git problem has a Stack Overflow answer
  • Hiring and onboarding — most developers already know Git

SVN tooling exists, but it feels like an afterthought in most modern pipelines.

Where SVN Still Makes Sense

I don't want this to be pure Git fan fiction. SVN still has real advantages in some situations:

  • Large binary files: game assets, design files, and CAD models don't bloat every clone's history, and file locking prevents unmergeable conflicts. This is the reason why I had to use SVN this time.
  • Partial checkouts: you can check out just one folder of a huge repo instead of everything.
  • Path-based access control: easy to restrict who can see or edit specific directories.
  • Simplicity: a smaller command set and a simpler mental model for non-developers.
  • Existing legacy systems: sometimes the company just uses SVN, and migrating isn't worth the risk.

Side-by-Side Comparison

Aspect SVN Git
Architecture Centralized Distributed
Offline work Very limited Full history and commits locally
Branching Directory copies, heavier Lightweight and instant
Merging Painful, tree conflicts Mature, well-tooled
Staging area No Yes
Large binaries Handles well Needs Git LFS
Partial checkout Natural Possible, but less natural
Ecosystem Shrinking Industry standard

My Verdict

After going back to SVN, my appreciation for Git went up a lot. It respects the way developers actually work: in small steps, with lots of experiments, and with the freedom to undo.

SVN feels like it was designed around the idea that the server is precious and the developer should be careful. Git feels designed around the idea that the developer should be free to experiment and the tool should have their back. I know which one I want in my daily workflow.

That said, if your team works mostly with large binary assets or needs strict directory-level control, SVN is still a legitimate choice. Just go in knowing the trade-offs!!
